## Context

The sharpest evidence against arkive is in arkive's own repository.

Current state, verified:

- `arkive/architecture.json` records **3 services** — `cli`, `viewer`,
  `architecture-store` — for a codebase containing an MCP server, HTTP server,
  schema layer, learning subsystem, scanner, drift engine, template system,
  prompt queue, snapshot store, and installer.
- `decisions: []`. **Zero recorded decisions** across ~20 commits that contained
  at least seven real ones: Zod for validation, the MCP SDK, Express for the
  viewer server, tsup for bundling, the confidence/provenance model, the
  snapshot system, the prompt queue, single-package MCP+viewer (with the
  stated reason — *"users want one install command, not two packages to
  coordinate"*).
- `dataFlows: []`.
- `lastUpdated` is 16 commits stale.
- A second, orphaned `architecture.json` sits at the repo root holding the
  original 4 decisions and 7 services, stranded by commit `62066bc`.
- `arkive/history/` was never created despite `init` creating it.
- Root `CLAUDE.md:5` says the repo is running in lightweight mode — no MCP, no
  viewer.

The original dogfood was good. Commit `6f8523b` produced a genuinely useful
document with real decisions including the React dedup problem and its
rejected alternative. It was abandoned within 48 hours and never recovered.

**If the thesis holds, the author is the primary user. The author did not adopt
it.** That is not a bug in the product — it is a signal that the cost exceeded
the benefit even for someone who understands it perfectly. Fixing this is the
test of whether the vision is real.

## Scope

1. **Recover.** Consolidate the orphaned root `architecture.json` with
   `arkive/architecture.json`. Nothing is discarded — the four lost decisions
   are recovered into the graph.
2. **Run the real tool.** `npx @ericjdz/arkive init` with MCP, viewer, and
   skills. Lightweight mode ends. If it does not survive its own installation
   on its own repository, that is a finding, and it goes in the issue tracker
   as a bug — not worked around.
3. **Backfill every node.** After 0005 and 0006, the derived graph should
   describe this codebase accurately and completely, generated by the tool,
   not typed by hand.
4. **Record the decisions.** Every real decision from the history, with its
   rejected alternative. Include the ones that were painful:
   - `curl | bash` installer running the wrong package name
   - post-commit hook passing a flag that does not exist
   - 659 lint errors shipping in v0.2.1
   - the path migration that orphaned the document
   - React 18/19 duplication
   These are precisely the decisions the product exists to capture, and
   capturing them is the demonstration.
5. **Dogfood the failure.** The workflow must catch a real regression. Change
   a module boundary, confirm drift fires, revert, confirm it clears. An
   architecture tracker that has never caught anything has not been tested.
6. **Make it a gate.** The repository's own architecture check runs in CI. If
   the document drifts from the code, the build fails. This is the dogfooding
   that compounds.

## Acceptance criteria

- [ ] `arkive/architecture.json` describes this repo accurately and is generated
      by the tool, not hand-maintained.
- [ ] Every node and edge carries provenance. Derived nodes marked `derived`.
- [ ] `decisions` is non-empty and every entry has a real rejected alternative.
- [ ] The four decisions from the orphaned root document are present.
- [ ] No second orphan exists at any legacy path.
- [ ] `arkive/history/` exists and is bounded.
- [ ] Introducing real drift fails the build; reverting passes it.
- [ ] The repository runs arkive in full mode, not lightweight.

## Note

Do this last. Doing it first means hand-maintaining a graph by hand, which is
precisely the failure mode the product exists to replace — and it would produce
a beautiful document that proves nothing.
